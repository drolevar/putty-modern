# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A WinUI 3 front end for PuTTY: a C# app (.NET 11, NativeAOT) on top of a native engine DLL built from the **unmodified** PuTTY core, which is the `external/putty` submodule ([drolevar/putty](https://github.com/drolevar/putty), a synchronized mirror of upstream, pinned at `29dd4b17`).

**State (2026-11-12): the skeleton works end to end and slices 1, 3, 4 and 5 are done; slice 2 awaits only a real-IME check; slice 6 (feature parity) and slice 7 (release) are done except what needs the owner: design decisions for the Transfers view, and the deferred packaging, ARM64 and AGENTS.md mirror; the serial path was checked by the owner by hand on COM4 (2026-11-12); CI on GitHub Actions is green (first run 2026-11-12).** Built and verified: the native engine DLL with its event loop and a headless session layer (`pe_session_*`: Seat and LogPolicy glue, raw and Telnet sessions tested against a loopback server), `PuTTY.Interop` (including `PuttySession`), and a `PuTTY.App` window that hosts the docking layout from the sketch and calls the engine, in both a normal build and a NativeAOT publish. A session can also get a terminal emulator that draws through a Direct2D renderer and takes keyboard input through a message hook and a port of PuTTY's `TranslateKey`; the app shows one in the docked document window (`PuTTY.App.exe --connect raw://host:port`, also `telnet://`, `rlogin://`), checked end to end under NativeAOT by `tools/app-terminal-smoke.ps1`. Mouse, selection, clipboard, scrollbar and scrollback work in the engine (tested through an offscreen view) and in the app under NativeAOT (the scrollbar by `tools/app-terminal-smoke.ps1`, the mouse, clipboard and wheel by `tools/app-mouse-e2e.ps1` with real input in Windows Sandbox). SSH login works in the engine and is tested against a test server (user name, password, keyboard-interactive and key-file authentication, host key confirmation, remote commands), and the app asks its questions in dialogs (`tools/app-ssh-smoke.ps1`, NativeAOT); a login to a real OpenSSH server (Win32-OpenSSH in the Sandbox) is checked end to end by `tools/app-openssh-smoke.ps1`. Saved PuTTY sessions are listed in the Sessions panel (in folders, with their host, and a RECENT list) and open on a double click (`tools/app-sessions-smoke.ps1`). The settings window (PuTTY's configuration box as a tree of pages in the sketch's words, `tools/app-settings-smoke.ps1`) creates, saves, opens and edits sessions, and PuTTY's Change Settings applies to a running one (Session details panel, checked in `tools/app-sessions-smoke.ps1`). Dragging a tab into a split group of its own and getting that layout back after a restart is checked with the real mouse in the Sandbox (`tools/app-workspace-smoke.ps1`). Not verified end to end: restoring a tab opened from the settings window (it is saved by where it connected, `SessionEndpoint`, and the code path has no end-to-end check). (Older note, beads `pp0.2` to `pp0.5`), IME composition (the proxy input box is built and its text path tested, but no IME composes in the Sandbox guest, so that step awaits a machine with a working IME), the details panel's key-exchange and host-key rows, CI, packaging. The tests are 191 in `PuTTY.Interop.Tests` (one inconclusive: the serial pair) (engine, sessions, SSH, saved sessions, the settings dialog) and 22 in `PuTTY.Sessions.Tests`, plus eleven end-to-end checks of the real app that run in Windows Sandbox (terminal, ssh, sessions, settings, openssh, workspace, appearance, features, agent, x11, crash). "Planned architecture" below is design intent, not code. Work is tracked in Beads (`bd ready`).

## Build, publish, run

Everything: `dotnet build PuTTY.slnx -c Release` builds the native engine and the managed projects, and stages `puttyengine.dll` next to `PuTTY.App` (from clean about 80 s; a no-change rebuild about 19 s). Native only: `build\native.cmd` (x64), which finds Visual Studio with `vswhere`, enters its developer environment and runs CMake with Ninja; output is `artifacts/native/x64/puttyengine.dll`. Nothing needs to be on PATH.

How it is wired: `src/PuTTY.Native` is a `Microsoft.Build.NoTargets` project (SDK version in `global.json`) whose only job is to run `build\native.cmd`; any project that imports `build/NativeEngine.targets` (the app and the test project) gets a `ReferenceOutputAssembly=false` reference to it so it builds first, plus a `StageNativeEngine` target that adds the DLL as content (not a static `Exists()` item, which is false on a clean tree). `native/CMakeLists.txt` builds PuTTY itself as an ExternalProject and links its static libraries from one flat `lib/` folder. It requires a single-config generator (Ninja) and stops with an error under a multi-config one.

Tests (MSTest via `MSTest.Sdk`, running on Microsoft.Testing.Platform; versions and the `dotnet test` runner are set in `global.json`):

```
dotnet test --solution PuTTY.slnx -c Release
dotnet test --project tests/PuTTY.Interop.Tests -c Release --filter "Name=Probe_runs_PuTTY_Conf_inside_the_engine"   # one test
```

They load the real `puttyengine.dll`, so a test run builds the native engine first. Note the MTP-mode syntax: `--solution`/`--project` flags, not positional paths. Tests host the engine the way the app will: `tests/PuTTY.Interop.Tests/EngineThread.cs` starts a dedicated thread that owns one engine instance and pumps its messages, and a test runs engine calls on it through `Run`. Each test gets a fresh engine, and the assembly is `[DoNotParallelize]` because PuTTY's core has global state.

NativeAOT publish: `dotnet publish src/PuTTY.App -c Release -r win-x64` writes `artifacts/publish/PuTTY.App/release_win-x64/PuTTY.App.exe` (about 11 MB plus the Windows App SDK files). A `PublishAot` project produces no `.exe` from plain `dotnet build`; to run a non-AOT build use `dotnet build src/PuTTY.App -c Release -p:PublishAot=false` (it writes `artifacts/bin/PuTTY.App/release_win-x64/PuTTY.App.exe`, **not** the publish folder, which keeps whatever AOT build was there: a UI check against the wrong exe once cost a debugging round, so look at the file's timestamp).

Checking the UI: **the owner wants every UI check to run in Windows Sandbox, never on the host desktop** (`tools/run-in-sandbox.ps1`, below). Inside it the tools are `winapp ui search "placeholder" -a PuTTY.App`, `winapp ui screenshot -a PuTTY.App --output ...`, `invoke`, `set-value`, `get-property`. Check content, not just chrome: under NativeAOT the window titles can render while the content is missing.

**UI checks run in the Sandbox (`tools/run-in-sandbox.ps1 [-Smoke terminal,ssh,sessions,settings,openssh,workspace,appearance,features,agent,x11,crash] [-AppDir ...] [-AttachDebugger]`).** It stages the app folder and `tools\` into `artifacts\sandbox-share\work` (the guest sees it as `C:\spike\work`), then runs `tools\sandbox\guest-run.ps1` for each check with `wsb exec -r ExistingLogin` (through a one-line `.cmd`, because `wsb` does not survive nested quotes), and prints the output that comes back through a file; the exit code is the number of `FAIL` lines. The Sandbox must be started by hand from the Start menu and logged in. **The guest has winget, Node LTS and the winapp CLI; install anything else missing there with winget** (the owner's rule: use the proper tool, do not write a stand-in; an earlier UI Automation stand-in for winapp was wrong and is gone). `guest-run.ps1` installs, once, what a check needs: the C++ runtime for `puttyengine.dll` (`winget install Microsoft.VCRedist.2015+.x64`) and, for the SSH checks, the test server's `ssh2` package (`tools\start-ssh-test-server.ps1 -Install`, into the shared folder). Traps: a process started by `wsb exec` has the environment of the logon, so `guest-run.ps1` reads PATH again from the registry; `powershell -File x.ps1 -Smoke a,b` passes `a,b` as one string (the runner splits it); `winapp ui focus` **refuses to act when the app's window is not in front** (an app started by `wsb exec` is not allowed to take the foreground), so the checks that type call `Focus-Terminal` (`tools\smoke-common.ps1`), which clicks inside the terminal as a user does; the smoke scripts refuse to run on the host unless `-AllowHostDesktop` is given; **the guest's screen is as big as the Sandbox window** (1006x677 once) and Windows does not let a window grow past the screen, so a check must not assume a size (the terminal check shrinks the window, then grows it to the screen). All eleven pass in the Sandbox on the NativeAOT build: terminal 14, ssh 17, sessions 72, settings 34, openssh 8, workspace 21, appearance 12, features 20, agent 11, x11 10, crash 12 checks (features 20 with the terminal's text read through UI Automation).

**Real OpenSSH (`-Smoke openssh`, `tools/app-openssh-smoke.ps1`):** `guest-run.ps1` installs Win32-OpenSSH with winget (`Microsoft.OpenSSH.Preview`, the server `sshd` too) and starts the service; the check makes a local account with `New-LocalUser` (**not `net user`: with a password longer than 14 characters it asks a question on the console and fails when nobody answers**) and deletes it again, connects to `ssh://puttytest@127.0.0.1:22`, answers the host key dialog (Connect Once, so nothing is written to the registry), gives a wrong password that OpenSSH refuses and PuTTY asks for again, then the right one, and types `echo ... > file` into the shell (OpenSSH on Windows starts `cmd`) whose file the script then reads. It found the use-after-free described under "SSH questions". `tools\sandbox-exec.ps1 '<cmd line>' [-RunAs System]` runs one command in the guest for installing and looking at things (winget, services, event log, files). **Crash in the guest:** WinDbg is installed there with winget; `tools\sandbox\install-debugger.ps1` (as System) copies `cdb` out of the locked package folder to `C:\debugger` and, with `-PageHeap`, turns full page heap on for `PuTTY.App.exe`; `run-in-sandbox.ps1 -AttachDebugger` then attaches `cdb` to the app in the checks that call `Attach-Debugger` (`smoke-common.ps1`; now openssh and workspace) and leaves the stacks of all threads in `results\cdb.log` and a dump in `results\crash.dmp` (commands in `tools\sandbox\cdb-crash-commands.txt`). Registering `cdb` as the post-mortem debugger (AeDebug) raced with the script's own cleanup and was dropped; an exit code of -1 is `Process.Kill()`. **A stowed exception (0xC000027B) is raised by `RaiseFailFastException`, which cdb sees only as a second-chance event:** `cdb-crash-commands.txt` gives those commands as `-c2` too, and `Attach-Debugger` no longer passes `-g` (with it the command file ran only at the first stop, which was the crash itself, too late to set the filters). The native stack of such a crash names no managed code: read `crash.log` first. **Real keyboard input and the foreground (needed by `-Smoke ime`, which injects keys with `SendInput`):** keys go to the foreground window, which an app started by `wsb exec` does not get by itself; the ime check takes it with `SwitchToThisWindow` plus attaching to the foreground thread (`SetForegroundWindow` alone, an Alt tap and `SPI_SETFOREGROUNDLOCKTIMEOUT` did not work). **A hung guest shell stops all of it:** when `Program Manager (Not Responding)` (a ghost window owned by `dwm.exe`) was the foreground, nothing could be raised; killing `explorer.exe` and starting it again with `wsb exec -r ExistingLogin -c C:\Windows\explorer.exe` fixed it. A leftover hung script holds its output file open and makes the next run print the old file, so a run that prints stale output means a stuck process in the guest. After a Sandbox restart, a TSF text service may stall the app on first activation (the UI thread sat in the service's own `FlushFileBuffers`, measured with `cdb -pv`); a non-invasive stack read of a hung app is `C:\debugger\cdb.exe -pv -p <pid> -c "~0kn 40;q"`.

- Debug information: the engine and PuTTY's libraries are compiled with `/Z7` and the DLL is linked with `/DEBUG /OPT:REF /OPT:ICF`, so `puttyengine.pdb` (about 7 MB, next to the DLL in `artifacts/native/x64`, staged by `NativeEngine.targets` into every output and the publish folder) names PuTTY's and our functions in a crash dump; code is the same as before. The flag reaches PuTTY's libraries only at a fresh configure (`CMAKE_C_FLAGS_INIT=/Z7` in `native/CMakeLists.txt`, which keeps the generator's `/DWIN32 /D_WINDOWS`): after changing it, delete `artifacts/native/x64/putty` (a from-scratch native build takes about 2 minutes).
- Why Ninja, measured for PuTTY's libraries from scratch: Ninja inside a VS developer environment configures in 25 s and builds in 51 s; the Visual Studio generator took 102 s and 107 s.
- Always build out-of-tree into `artifacts/` (git-ignored). Never build inside `external/putty`. A bash `cd` into it persists across tool calls in this environment, so use absolute paths.
- `plink` in `external/putty/CMakeLists.txt` is the template for which libraries an SSH client links. `guiterminal` bundles root `terminal/`, `ldisc.c`, `config.c`, `dialog.c` **plus** the Windows GUI files (`windows/dialog.c`, `controls.c`, ...), so link order matters if our engine defines its own `dlg_*` functions. The default engine links PuTTY's whole SSH client, backends, network code and portable terminal code (`terminal.c`, `bidi.c`, `lineedit.c`, `ldisc.c`, compiled directly), so `dotnet build` itself proves the front-end contract is met for all of that. The settings dialog's description (`config.c`, `dialog.c`) is compiled in too, with `native/engine/configbox.c` as its front end (the 30 `dlg_*` functions and `show_ca_config_box`), so the whole front-end contract of `docs/front-end-contract.md` is met at link time. The old `build\native.cmd x64 full` configuration, which was expected to fail and list what was missing, is gone.
- Shell traps in Git Bash: it rewrites MSVC-style `/flags` into paths (`dumpbin /nologo` fails), so `export MSYS_NO_PATHCONV=1`; and `cmd | tail` hides a failing exit code (a native build once reported exit 0 while failing), so use `set -o pipefail` and check `${PIPESTATUS[0]}`.

## Constraints that are not obvious

1. **PuTTY's CMake must be the top-level project.** It uses `${CMAKE_SOURCE_DIR}` about 96 times (including `charset/` and `cmake/gitcommit.cmake`). Never `add_subdirectory(external/putty)` from our own CMake; build it as a separate configure (for example via `ExternalProject`) and link its static libraries.
2. **No C++ file can include PuTTY headers.** `ssh.h` uses `new` as a vtable member name (lines 757, 834, 890, 1097). Code that talks to PuTTY (Seat, TermWin, LogPolicy, key translation) must be C. C++ (the Direct2D/DirectWrite renderer) sits behind a C interface.
3. **Keep `external/putty` pristine** so it can track upstream. Hooks the UI needs must live in our code or a fork branch. Example: the sketch's session inspector needs key-exchange, cipher and host-key fingerprint, and `putty.h` has no accessor for them.
4. **The core is single-threaded with global state** (timer queue, callback queue, PRNG, handle-wait list). `windows/handle-wait.c` asserted at most 64 waitable handles (the engine replaces it, `native/engine/handlewait.c`, see "Handle waits" below), and `cleanup_exit` terminates the process. Both matter once many sessions share one process.
5. **Never compile PuTTY code with `NDEBUG`** (`defs.h` errors out; assertions are part of its security model). `native/CMakeLists.txt` strips `/DNDEBUG` from the engine's flags. PuTTY's libraries are always built Release (`/MD`), so the engine always uses `/MD` too, even in its Debug configuration (mixing `/MD` and `/MDd` fails to link).
6. **The engine must define the functions PuTTY expects from a front end.** Linking `utils` alone needed only `modalfatalbox` and `cleanup_exit` (both in `native/engine/frontend.c`); the whole SSH client needed 14 more (printing, jump list, process-level), now defined in `frontend.c` or supplied by PuTTY's own stubs (`stubs/no-printing.c`, `windows/no-jump-list.c`), and the settings dialog still needs 31 (`docs/front-end-contract.md`). Do not link PuTTY's `guiterminal` library to make them go away: it bundles PuTTY's Win32 dialog code and silently hides what the engine must implement. Do not use `stubs/no-ca-config.c`: it is for programs without SSH code, and our engine links the real `ssh/ca-config.c`. The `Seat`, `TermWin` and `LogPolicy` obligations are runtime vtables the linker cannot check.
7. **PuTTY's assertions are live and mean it.** A crash like `Assertion failed ... tree234.c` kills the host process and is almost always misuse of a PuTTY API by our glue, not a PuTTY bug. Example seen: a timer scheduled with a `NULL` context (`schedule_timer(ms, fn, NULL)`) asserts in `run_timers`, because the context identifies the owner for `expire_timer_context`; timer contexts must be non-NULL. A second one: `conf_get_int(conf, CONF_tcp_keepalives)` asserts in `conf.c`, because that key is a boolean; the accessor must match the key's value type, so copy the call from `windows/window.c` or `windows/putty.c` instead of guessing (`conf_get_bool` here).

## NativeAOT + WinUI 3 on .NET 11 (verified on 11.0.100, first on rc.3, with Windows App SDK 2.6.5)

`PuTTY.App` is unpackaged (`WindowsPackageType=None`, self-contained Windows App SDK) and package-free by design; MSIX packaging is a separate step with `winapp package` (issue `putty-modern-apl`). The settings below live in `src/PuTTY.App/PuTTY.App.csproj` and each has a comment there; do not remove them without re-testing a NativeAOT publish **and** launching the result.

- **`UseOptimizedPublish=false`** (WindowsAppSDK [#6897](https://github.com/microsoft/WindowsAppSDK/issues/6897)): on the .NET 11 SDK, `PublishAot` turns on optimized publish, and XAML compilation then fails with `WMC1007`. This hits unpackaged apps too, not only single-project MSIX. The issue is fixed but unreleased. Re-tested on the 11.0.100 final SDK: removing the setting still fails (now as `MSB3030`, `PuTTY.App.pri` not found), so it stays.
- **`Microsoft.Windows.SDK.BuildTools.MSIX` pinned to 1.7.261102100** (WindowsAppSDK [#6394](https://github.com/microsoft/WindowsAppSDK/issues/6394), fixed from 1.7.260930100): Windows App SDK 2.6.5 pulls 1.7.251221100 transitively, so the pin relies on `CentralPackageTransitivePinningEnabled` in `Directory.Packages.props`. The publish output has no loose `.xbf` files (XAML is in `PuTTY.App.pri`) and the app starts fine.
- **`AllowUnsafeBlocks`** is required (CsWinRT error CsWinRT1030) because the docking library's types implement generic WinRT interfaces.
- **Under NativeAOT a WinUI class that managed code only ever receives from native code comes back as its nearest known base class** (cause of what used to be "the content of docked windows is silently dropped", Beads `putty-modern-sqm`, solved). The projection turns a native object into a managed one by its runtime class name; if the trimmer finds no use of that class, the lookup falls back to a base class, so `GetTemplateChild("PART_X") as ContentPresenter` is **null**, with no error. Measured in this app without any workaround: a `ContentPresenter` (from `XamlReader.Load`) came back as `FrameworkElement`, `Rectangle`, `Border` and `FontIcon` likewise, `Button` and `ToggleButton` and `ScrollViewer` as `ContentControl`/`ButtonBase`, `Canvas` as `Panel`, while `TextBlock`, `Grid` and `StackPanel` (constructed somewhere) were exact. `Digi21.WinUI.Docking` plugs its windows into a `ContentPresenter` it gets from its template, so the windows never appeared; its Close and pin buttons are `as Button` casts, so they did nothing. Constructing one instance of each such class in reachable code fixes it: `src/PuTTY.App/AotTypeAnchors.cs` (called from the `App` constructor) did that for the five classes the library casts to (`ContentPresenter`, `Rectangle`, `Border`, `Button`, `FontIcon`) **until the library fixed it itself (2026-11-13: `TemplatePart<T>` and `As<T>` in `Digi21.WinUI.Docking` 1.6.1-alpha.0.6, see External references); those five are gone, checked by the owner in the published app without them (docked content, glyphs and Close buttons right), and only the `Style` anchor for the app's own `AccentButtonStyle` cast is left**, and it replaced the old `TrimmerRoots.xml` (a `DockSite` root), which fixed only `ContentPresenter` by accident: with it the Close button still did nothing. Verified on the 11.0.100 final SDK: no root plus the anchors gives 3 of 3 placeholders and a Close button that closes its window (invoked through UI Automation). **Whenever managed code casts a native object to a WinUI class it does not construct, add it to the anchors**, and check it by loading the class with `XamlReader.Load("<X xmlns='http://schemas.microsoft.com/winfx/2006/xaml/presentation'/>")` and looking at `GetType()`. The same applies to `FindName`, `VisualTreeHelper` and anything else that hands back an object created by native code. Not the cause, each tried: the library built from source against Windows App SDK 2.6.5 on net11, `IsAotCompatible`, wrapping every type in a trimmer root (`DockSite`, the containers, the whole assembly all "fixed" it only because they happen to keep some constructions alive).
- The write-up, including the original table of what was tried (which preserved types made the content appear), is in `docs/nativeaot.md` on the fork branch `nativeaot-readiness` ([drolevar/DockingPanels](https://github.com/drolevar/DockingPanels/tree/nativeaot-readiness)), together with a small library change (`AllowUnsafeBlocks`). The owner asked that any improvement to the library be done in that fork; nothing has been sent to the upstream repository, so ask before opening an issue or pull request there. The library-side fix is now written differently (`TemplatePart<T>` and `As<T>` keep the classes a cast names, and a banned-API check stops a new direct `GetTemplateChild`): commit `2e99a5c`, pull request #4 upstream, in the package the app uses (see External references). **With that package the five anchors were removed** (the published app was run without them: docked content, glyphs and Close buttons fine); the old local branch `aot-template-part-types` is superseded. Whenever the **app's own** code casts a native object to a WinUI class it does not construct, it still needs an anchor.
- **A C# subclass of a WinUI control must be `partial` for NativeAOT.** An unmarked one crashed the spike's AOT build at the first frame with `COMException 0x80040111 (ClassFactory cannot supply requested class)` naming `Windows.ApplicationModel.LimitedAccessFeatures`, which is misleading; the real signal was a **CsWinRT1028** warning ("isn't marked partial") that a filtered build log had hidden. Marking it `partial` fixes it (`spikes/keyboard-ime/SubclassProbe.cs`, `--probe-partial` / `--probe-plain`). **Read every CsWinRT warning in a NativeAOT publish**; do not grep the log for only `error|warning CS|IL`.
- WinUI template (`winapp new`) facts, if you scaffold another project: it targets net10 and is packaged by default, and it uses unpinned `Version="*"` references that must move into central package management.

## Planned architecture

```
external/putty/        submodule (pristine)                                   exists
native/                our C/C++ only: CMakeLists, CMakePresets, engine/      exists (C-ABI skeleton)
build/native.cmd       builds the native engine (CMake + Ninja, VS dev env)    exists
src/PuTTY.Native/      NoTargets project that runs build\native.cmd            exists
src/PuTTY.Interop/     LibraryImport declarations, AOT-compatible             exists
src/PuTTY.App/         WinUI 3 app, unpackaged, PublishAot, placeholder UI    exists
build/NativeEngine.targets  shared: build native first, stage the DLL          exists
tests/PuTTY.Interop.Tests/  MSTest, loads the real native engine               exists
spikes/keyboard-ime/   throwaway keyboard/IME experiment, not in PuTTY.slnx      exists
```

- **Layers:** PuTTY core (C) -> engine DLL (C glue plus C++ renderer, flat C ABI) -> `PuTTY.Interop` -> WinUI 3 app. Interop uses `LibraryImport`, `[assembly: DisableRuntimeMarshalling]`, blittable signatures and `[UnmanagedCallersOnly]` callbacks. Sessions are deliberately **not** `SafeHandle`s (see "Sessions" below). The engine starts as a DLL; static linking is a later option.
- **What gets replaced vs reused** (see the PuTTY map below): replace the `windows/` GUI group (`window.c`, `dialog.c`, `controls.c`, `config.c`, `putty.c`, `select-gui.c`, ...). Reuse the platform layer (`network.c`, `handle-io.c`, `storage.c`, `noise.c`, `serial.c`, `conpty.c`, `agent-client.c`, `sharing.c`, `gss.c`, `utils/`).
- **Threading (implemented in `native/engine/eventloop.c`):** the engine lives on the one thread that calls `pe_init`, which must run a Win32 message loop (the WinUI UI thread does; tests call `pe_pump`). A hidden message-only window receives `WM_NETEVENT` (forwarded to `winselgui_response`); `setup_gui_timing` supplies timers; `request_callback_notifications` posts a message that runs **one** deferred callback and re-posts while more are queued, like PuTTY's own loop, so window messages are not starved. Every other `pe_*` call from a different thread returns `PE_ERR_THREAD`. `pe_shutdown` closes sockets and drains messages before destroying the window (a stale entry in `select-gui.c`'s moribund-socket set would make a later socket that reuses a handle value ignore its events). The handle waits that PuTTY's own event loops would run are in `handlewait.c` (below).
- **Sessions (implemented in `native/engine/session.c`, managed side `src/PuTTY.Interop/PuttySession.cs`):** a `pe_session` owns a `Seat`, a `LogPolicy`, a `Conf` (from `load_open_settings(NULL, ...)` defaults for now), a `LogContext` and a `Backend`. Output, log lines, errors and close go to the host through the blittable `pe_session_events` table; the managed side turns them into `Output`/`Log`/`Error`/`Closed` events on the engine thread, and every `[UnmanagedCallersOnly]` callback catches all exceptions. Things that are easy to get wrong:
  - `PuttySession` is two-phase (construct, subscribe, then `Start()`) so the first lines of the event log are not lost: PuTTY logs "Connecting to ..." from inside `backend_init`.
  - `Closed` is raised **once**: PuTTY documents that `notify_remote_disconnect` may arrive more than once, even while `backend_connected()` is still true, so the glue ignores it until the backend says the connection is gone, and `connection_fatal` always closes; a flag makes whichever comes first the only notification.
  - A handler may dispose the session it is being called for. PuTTY is still on the stack inside the backend then, so `pe_session_close` from inside a callback marks the session `pending_close` (events are silenced at once) and queues the teardown with `queue_toplevel_callback`. A live-session list validates handles, so a stale `pe_session*` is rejected rather than dereferenced.
  - `PuttySession` is a plain `IDisposable`, not a `SafeHandle`: a `SafeHandle` is released on the finalizer thread, and the engine refuses calls from any thread but its own (`PE_ERR_THREAD`). A session that is never disposed is closed by `pe_shutdown` (`pe_sessions_close_all`), and disposing it afterwards is harmless.
  - **`session_start` calls PuTTY's `prepare_session(conf)`**, which PuTTY's own launcher (`windows/putty.c`, `cfg_launch`) does and a front end that replaces it must too: `user@host` in the Host Name box becomes a user name and a host (the last `@` counts), a `:port` suffix is dropped, whitespace is trimmed. Without it a saved session whose host reads `me@server` was looked up as a host name and the user got "Error 11003: A non-recoverable error occurred during a database lookup" (found from the diagnostic log, 2026-11-12; `SavedSessionTests.A_user_at_host_in_the_host_name_is_split_before_connecting`). It works on the session's own copy of the Conf, so the registry is untouched, and the host the backend gets is read back from the Conf.
  - Not done yet: `Seat` prompts (`get_userpass_input`), host-key and cipher confirmations (they fail safe through the `nullseat_*` defaults, slice 3), `Conf` is not yet configurable from the host. Warnings that belong to no session (`nonfatal()`, `old_keyfile_warning()`) are forwarded: `frontend.c` calls the handler set with `pe_set_warning_handler` (dropped by `pe_shutdown`, registered again by `PuttyEngine.Initialize`), which raises `PuttyEngine.Warning` on the engine thread; without a subscriber they only reach the debugger.
- **Renderer (`native/engine/render.cpp`, interface in `render.h`):** C++ (it cannot see PuTTY headers), Direct2D and DirectWrite, drawing a grid of cells one glyph per cell so fallback fonts cannot misalign it. Two targets with one drawing path: offscreen (a WIC bitmap, software, used by the tests: no window, no GPU) and a DXGI composition swap chain plugged into a XAML `SwapChainPanel` through `Microsoft.UI.Xaml.Media.DXInterop.ISwapChainPanelNative` (IID `63aad0b8-...`, not the UWP one). Panel drawing goes to a persistent canvas bitmap that is copied to the swap chain on each present, because a flip-model back buffer does not keep its contents and the emulator repaints only what changed. The panel path is not exercised until the terminal view exists (Beads `88o.5`). `pe_diag_render_text` / `PuttyEngine.Diagnostics.RenderText` draw text offscreen and report cell size and per-cell ink, which `RenderTests` use.
- **Line drawing and block characters are drawn by the renderer, not the font (`native/engine/boxdraw.h`, hooked at the top of `pe_render_glyph`; tests `BoxDrawingTests`):** U+2500..U+259F are built from rectangles that run to the cell's edges. The font's own glyphs span its unrounded ascent and descent while a cell is a whole number of pixels (`pe_render_set_font` rounds the line height up), so with some fonts and sizes (Consolas at 20 px with a 24 px cell, Courier New at 15 px with 17) a column of `│` had a one-pixel gap at every row boundary; found by the owner in Midnight Commander on a serial line, 2026-11-12. Light, heavy and double lines with their junctions (a table generated from the Unicode character names, 128 entries; double lines stop at the inner line of a double neighbour, so `╔╦╗ ╠╬╣ ╚╩╝` and the mixed single/double ones close properly), the block elements (halves, eighths, quadrants, the shades as the foreground at 25/50/75 percent over the background already drawn) and the diagonals. Dashed lines are drawn solid and arcs as square corners. A light line is `round(cell width / 8)` pixels, at least 1, so at normal sizes thinner than a font's anti-aliased 2-pixel stem. `std::max` needs parentheses in that header (`windows.h` defines `max`). **Powerline separators U+E0B0..U+E0BF** (triangles, half circles and their outlines, the corner triangles, slashes) are drawn there too as vector shapes that fill the cell, so they work with any font, including one that has no Powerline glyphs (it would show a missing-glyph box); the other Powerline and Nerd Font symbols (branch U+E0A0, line number, lock) are left to the font, so they need a Powerline or Nerd Font. A triangle's corners are covered by part of a pixel, so tests check the flat side in the middle of the row.

- **Mouse, selection, clipboard, scrollback (engine side in `session.c`, `termwin.c`; managed `PuttySession.Mouse/Wheel/Scroll/Paste`, events `ClipboardWrite`, `ClipboardPasteRequested`, `ScrollbarChanged`):** the host passes pointer events in view pixels (physical, like the renderer) with modifiers and a timestamp; the engine turns them into cells and calls `term_mouse`, ported from `windows/window.c`'s `TranslateButton`/`click` logic: button mapping by `CONF_mouse_is_xterm`, double and triple clicks from the timestamp and `GetDoubleClickTime`, drags only while a button is down, raw mouse reporting (a program that asked for it gets the xterm escape sequences, and Shift overrides when `CONF_mouse_override`), a right click with Ctrl or in Windows mouse style does nothing in the engine (the host owns menus). - **SSH questions: prompts, host keys, options (engine `session.c`; managed `PuttySession.Interaction.cs`; tests `SshTests`):** the Seat answers PuTTY's questions through host events instead of PuTTY's modal dialogs. `get_userpass_input` (user name, password, key passphrase, keyboard-interactive) becomes `PromptRequested` with `Name`, `Instruction`, `Fields` (text and echo flag) and `FromServer`; `confirm_ssh_host_key`, `confirm_weak_crypto_primitive` and `confirm_weak_cached_hostkey` become `ConfirmationRequested` with the dialog text exactly as PuTTY words it (`Items`: paragraph, display = the fingerprint, scary heading when a key has **changed**, title ...). - **Handle waits (`native/engine/handlewait.c`, tests `ProxyTests`):** PuTTY keeps a list of HANDLEs to wait for (`add_handle_wait`) and expects its front end's loop to wait on them; the engine has no loop of its own (the host's message loop runs on the engine thread), so **nothing ever waited and everything built on handles was dead**: `handle-io.c` (pipes, files, the serial line, a local proxy command, the OpenSSH agent's named pipe: they all signal its one `ready_event`), ConPTY and Pageant. `handlewait.c` defines all five functions of PuTTY's `handle-wait.c` (so the linker never takes PuTTY's version): each wait is a thread-pool wait (`RegisterWaitForSingleObject`, which also lifts the 64-handle limit); when a handle is signalled the pool posts `PE_WM_HANDLE_WAIT` to the engine's window and the engine thread runs the callback, then arms the wait again (a handle that is still signalled fires again, as in PuTTY's loop). The pool callback only posts a message and carries an id, not a pointer, so a message that arrives after the wait was deleted finds nothing. `pe_shutdown` disarms what is left but **keeps the entries**: handle-io.c creates its one `ready_event` and registers its wait once per process (`ensure_ready_event_setup`), so an engine that dropped the entry at shutdown left every later engine in the process (a restart, the next test) with handle I/O that never woke up; found on a host with a real Pageant running (its named pipe was the first user), where the second `PortForwardingTests` test hung at "Pageant is running. (2) **Closing a session while a proxy was still negotiating was a double free**: the proxy borrows the backend's Seat (a TempSeat), and PuTTY's `raw_free` (and the Telnet and Rlogin ones) frees that TempSeat first and then closes the socket, whose cleanup returns the seat through the pointer just freed; `session_destroy` now calls `interactor_return_seat(backend->interactor)` first (a no-op when nothing was borrowed); `ProxyTests.Closing_a_session_while_the_proxy_is_still_negotiating_is_safe`. - **Fatal errors (`pe_set_fatal_handler`, `PuttyEngine.Fatal`, `App.OnEngineFatal`, `FatalBox`, `tools/app-crash-smoke.ps1`):** some errors end the whole process and so every session: PuTTY's `modalfatalbox` (out of memory and the like), a failed assertion in its code (its assertions are live), anything that makes the C runtime abort. The engine tells the host first (`pe_set_fatal_handler`, registered again by `PuttyEngine.Initialize`, dropped by `pe_shutdown`; called once, on the thread that hit the error): the app (`App.OnEngineFatal`) writes the reason to the crash log, **saves its workspace (`MainWindow.SaveWorkspace`), so the next start brings the tabs back**, and shows a native message box (`FatalBox`, not XAML: the process is going down inside native code on the UI thread; not shown under the test hook). `modalfatalbox` then ends the process at once with **exit code 3** (`TerminateProcess`: PuTTY's own expected way to die, no crash report; without a handler it aborts as before), `cleanup_exit` with its own code. An assertion arrives as SIGABRT (`pe_fatal_install`, called by `pe_init`: it also sets `_set_error_mode(_OUT_TO_STDERR)` and removes the abort message box, so an assertion no longer stops at a box) and the handler returns to let the abort go on, so a debugger or Windows Error Reporting still sees it (exit code 0xC0000409); **the assertion's own text goes to standard error, which a GUI process cannot show, so the host is told only that "an assertion failed" (run from a console to read it)**. - **Port forwarding (`PortForwardingTests`, the Node test server's `tcpip` and `tcpip-forward` handlers):** the Tunnels page is PuTTY's own and the forwarding itself is PuTTY's `portfwd.c`; nothing had to be added to the engine, the tests are the evidence that it works behind our event loop: a saved session whose `PortForwardings` value lists the forwards (`L5555=127.0.0.1:7000` local, `R5000=127.0.0.1:7000` remote, `D1080` dynamic: PuTTY opens a SOCKS server) carries data through the test SSH server to an echo server, in all three directions; a server started with `--no-forwarding` makes PuTTY close the connection and say "refused" in the event log. - **Appearance of a session: font and bell (`TerminalFont.cs`, `WindowFlash.cs`, `pe_session_get_font`, `tw_bell` in `termwin.c`; tests in `TerminalViewTests`, check `tools/app-appearance-smoke.ps1`):** the renderer takes its font from the host, so the host asks what the session wants: `PuttySession.GetFont()` (`pe_session_get_font`: PuTTY's `CONF_font` as name, height - positive points, negative pixels - and bold). `TerminalFont.For(session)` uses it, **except when it is PuTTY's built-in default (Courier New, 10 point)**, which is what every session has that never chose a font: that means the app's own choice, Cascadia Mono then Consolas at 15 DIPs. What the engine had to supply is the answer to "the log file exists already and the settings say ask": `LogPolicy.askappend` now raises a `ConfirmationRequested` of kind `LogFileExists` (`PE_CONFIRM_LOG_FILE_EXISTS`; `Host` is the path) and answers through `Overwrite()`, `Append()` or `Cancel()` (= logging off for the session, the connection goes on), inside the handler or later: `askappend` returns -1 and `logging.c` queues what is to be logged until the callback (mode 0 off, 1 append, 2 overwrite; **the numbers are not in that order in the settings: LGXF_OVR is 1, LGXF_APN 0, LGXF_ASK -1**). A session is named by pointer **and a serial number that is never reused** (`pe_session.serial`), because a dialog may outlive its session and a new one can get the same address: Apply on a gone session is `PE_ERR_STATE`; `pe_config_start_session` refuses such a dialog (the refusal shows at `Start()`, `CreateSession` is two-phase).
