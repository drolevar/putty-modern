# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A WinUI 3 front end for PuTTY: a C# app (.NET 11, NativeAOT) on top of a native engine DLL built from the **unmodified** PuTTY core, which is the `external/putty` submodule ([drolevar/putty](https://github.com/drolevar/putty), a synchronized mirror of upstream, pinned at `29dd4b17`).

**State (2026-11-11): the skeleton works end to end and slices 1, 3 and 4 are done; slice 2 awaits only a real-IME check, slice 5 (the workspace) has not started.** Built and verified: the native engine DLL with its event loop and a headless session layer (`pe_session_*`: Seat and LogPolicy glue, raw and Telnet sessions tested against a loopback server), `PuTTY.Interop` (including `PuttySession`), and a `PuTTY.App` window that hosts the docking layout from the sketch and calls the engine, in both a normal build and a NativeAOT publish. A session can also get a terminal emulator that draws through a Direct2D renderer and takes keyboard input through a message hook and a port of PuTTY's `TranslateKey`; the app shows one in the docked document window (`PuTTY.App.exe --connect raw://host:port`, also `telnet://`, `rlogin://`), checked end to end under NativeAOT by `tools/app-terminal-smoke.ps1`. Mouse, selection, clipboard, scrollbar and scrollback work in the engine (tested through an offscreen view) and in the app under NativeAOT (the scrollbar by `tools/app-terminal-smoke.ps1`, the mouse, clipboard and wheel by `tools/app-mouse-e2e.ps1` with real input in Windows Sandbox). SSH login works in the engine and is tested against a test server (user name, password, keyboard-interactive and key-file authentication, host key confirmation, remote commands), and the app asks its questions in dialogs (`tools/app-ssh-smoke.ps1`, NativeAOT); a login to a real OpenSSH server (Win32-OpenSSH in the Sandbox) is checked end to end by `tools/app-openssh-smoke.ps1`. Saved PuTTY sessions are listed in the Sessions panel (in folders, with their host, and a RECENT list) and open on a double click (`tools/app-sessions-smoke.ps1`). The settings window (PuTTY's configuration box as a tree of pages in the sketch's words, `tools/app-settings-smoke.ps1`) creates, saves, opens and edits sessions, and PuTTY's Change Settings applies to a running one (Session details panel, checked in `tools/app-sessions-smoke.ps1`). Not verified end to end: dragging a tab into a split group and restoring that (the library saves it, the app has no test that drags) and restoring a tab opened from the settings window (it is saved by where it connected, `SessionEndpoint`, and the code path has no end-to-end check). (Older note, beads `pp0.2` to `pp0.5`), IME composition (the proxy input box is built and its text path tested, but no IME composes in the Sandbox guest, so that step awaits a machine with a working IME), the details panel's key-exchange and host-key rows, CI, packaging. The tests are 118 in `PuTTY.Interop.Tests` (engine, sessions, SSH, saved sessions, the settings dialog) and 22 in `PuTTY.Sessions.Tests`, plus six end-to-end checks of the real app that run in Windows Sandbox (terminal, ssh, sessions, settings, openssh, workspace). "Planned architecture" below is design intent, not code. Work is tracked in Beads (`bd ready`).

## Build, publish, run

Everything: `dotnet build PuTTY.slnx -c Release` builds the native engine and the managed projects, and stages `puttyengine.dll` next to `PuTTY.App` (from clean about 80 s; a no-change rebuild about 19 s). Native only: `build\native.cmd` (x64), which finds Visual Studio with `vswhere`, enters its developer environment and runs CMake with Ninja; output is `artifacts/native/x64/puttyengine.dll`. Nothing needs to be on PATH.

How it is wired: `src/PuTTY.Native` is a `Microsoft.Build.NoTargets` project (SDK version in `global.json`) whose only job is to run `build\native.cmd`; any project that imports `build/NativeEngine.targets` (the app and the test project) gets a `ReferenceOutputAssembly=false` reference to it so it builds first, plus a `StageNativeEngine` target that adds the DLL as content (not a static `Exists()` item, which is false on a clean tree). `native/CMakeLists.txt` builds PuTTY itself as an ExternalProject and links its static libraries from one flat `lib/` folder. It requires a single-config generator (Ninja) and stops with an error under a multi-config one.

Tests (MSTest via `MSTest.Sdk`, running on Microsoft.Testing.Platform; versions and the `dotnet test` runner are set in `global.json`):

```
dotnet test --solution PuTTY.slnx -c Release
dotnet test --project tests/PuTTY.Interop.Tests -c Release --filter "Name=Probe_runs_PuTTY_Conf_inside_the_engine"   # one test
```

They load the real `puttyengine.dll`, so a test run builds the native engine first. Note the MTP-mode syntax: `--solution`/`--project` flags, not positional paths. Tests host the engine the way the app will: `tests/PuTTY.Interop.Tests/EngineThread.cs` starts a dedicated thread that owns one engine instance and pumps its messages, and a test runs engine calls on it through `Run`. Each test gets a fresh engine, and the assembly is `[DoNotParallelize]` because PuTTY's core has global state.

NativeAOT publish: `dotnet publish src/PuTTY.App -c Release -r win-x64` writes `artifacts/publish/PuTTY.App/release_win-x64/PuTTY.App.exe` (about 11 MB plus the Windows App SDK files). A `PublishAot` project produces no `.exe` from plain `dotnet build`; to run a non-AOT build use `dotnet build src/PuTTY.App -c Release -p:PublishAot=false` (it writes `artifacts/bin/PuTTY.App/release_win-x64/PuTTY.App.exe`, **not** the publish folder, which keeps whatever AOT build was there: a UI check against the wrong exe once cost a debugging round, so look at the file's timestamp).

Checking the UI: **the owner wants every UI check to run in Windows Sandbox, never on the host desktop** (`tools/run-in-sandbox.ps1`, below). Inside it the tools are `winapp ui search "placeholder" -a PuTTY.App`, `winapp ui screenshot -a PuTTY.App --output ...`, `invoke`, `set-value`, `get-property`. Check content, not just chrome: under NativeAOT the window titles can render while the content is missing.

**UI checks run in the Sandbox (`tools/run-in-sandbox.ps1 [-Smoke terminal,ssh,sessions,settings,openssh,workspace] [-AppDir ...] [-AttachDebugger]`).** It stages the app folder and `tools\` into `artifacts\sandbox-share\work` (the guest sees it as `C:\spike\work`), then runs `tools\sandbox\guest-run.ps1` for each check with `wsb exec -r ExistingLogin` (through a one-line `.cmd`, because `wsb` does not survive nested quotes), and prints the output that comes back through a file; the exit code is the number of `FAIL` lines. The Sandbox must be started by hand from the Start menu and logged in. **The guest has winget, Node LTS and the winapp CLI; install anything else missing there with winget** (the owner's rule: use the proper tool, do not write a stand-in; an earlier UI Automation stand-in for winapp was wrong and is gone). `guest-run.ps1` installs, once, what a check needs: the C++ runtime for `puttyengine.dll` (`winget install Microsoft.VCRedist.2015+.x64`) and, for the SSH checks, the test server's `ssh2` package (`tools\start-ssh-test-server.ps1 -Install`, into the shared folder). Traps: a process started by `wsb exec` has the environment of the logon, so `guest-run.ps1` reads PATH again from the registry; `powershell -File x.ps1 -Smoke a,b` passes `a,b` as one string (the runner splits it); `winapp ui focus` **refuses to act when the app's window is not in front** (an app started by `wsb exec` is not allowed to take the foreground), so the checks that type call `Focus-Terminal` (`tools\smoke-common.ps1`), which clicks inside the terminal as a user does; the smoke scripts refuse to run on the host unless `-AllowHostDesktop` is given; **the guest's screen is as big as the Sandbox window** (1006x677 once) and Windows does not let a window grow past the screen, so a check must not assume a size (the terminal check shrinks the window, then grows it to the screen). All six pass in the Sandbox on the NativeAOT build: terminal 14, ssh 17, sessions 72, settings 34, openssh 8, workspace 20 checks.

**Real OpenSSH (`-Smoke openssh`, `tools/app-openssh-smoke.ps1`):** `guest-run.ps1` installs Win32-OpenSSH with winget (`Microsoft.OpenSSH.Preview`, the server `sshd` too) and starts the service; the check makes a local account with `New-LocalUser` (**not `net user`: with a password longer than 14 characters it asks a question on the console and fails when nobody answers**) and deletes it again, connects to `ssh://puttytest@127.0.0.1:22`, answers the host key dialog (Connect Once, so nothing is written to the registry), gives a wrong password that OpenSSH refuses and PuTTY asks for again, then the right one, and types `echo ... > file` into the shell (OpenSSH on Windows starts `cmd`) whose file the script then reads. It found the use-after-free described under "SSH questions". `tools\sandbox-exec.ps1 '<cmd line>' [-RunAs System]` runs one command in the guest for installing and looking at things (winget, services, event log, files). **Crash in the guest:** WinDbg is installed there with winget; `tools\sandbox\install-debugger.ps1` (as System) copies `cdb` out of the locked package folder to `C:\debugger` and, with `-PageHeap`, turns full page heap on for `PuTTY.App.exe`; `run-in-sandbox.ps1 -AttachDebugger` then attaches `cdb` to the app in the checks that call `Attach-Debugger` (`smoke-common.ps1`; now only openssh) and leaves the stacks of all threads in `results\cdb.log` and a dump in `results\crash.dmp` (commands in `tools\sandbox\cdb-crash-commands.txt`). Registering `cdb` as the post-mortem debugger (AeDebug) raced with the script's own cleanup and was dropped; an exit code of -1 is `Process.Kill()`. **Real keyboard input and the foreground (needed by `-Smoke ime`, which injects keys with `SendInput`):** keys go to the foreground window, which an app started by `wsb exec` does not get by itself; the ime check takes it with `SwitchToThisWindow` plus attaching to the foreground thread (`SetForegroundWindow` alone, an Alt tap and `SPI_SETFOREGROUNDLOCKTIMEOUT` did not work). **A hung guest shell stops all of it:** when `Program Manager (Not Responding)` (a ghost window owned by `dwm.exe`) was the foreground, nothing could be raised; killing `explorer.exe` and starting it again with `wsb exec -r ExistingLogin -c C:\Windows\explorer.exe` fixed it. A leftover hung script holds its output file open and makes the next run print the old file, so a run that prints stale output means a stuck process in the guest. After a Sandbox restart, a TSF text service may stall the app on first activation (the UI thread sat in the service's own `FlushFileBuffers`, measured with `cdb -pv`); a non-invasive stack read of a hung app is `C:\debugger\cdb.exe -pv -p <pid> -c "~0kn 40;q"`.

- Debug information: the engine and PuTTY's libraries are compiled with `/Z7` and the DLL is linked with `/DEBUG /OPT:REF /OPT:ICF`, so `puttyengine.pdb` (about 7 MB, next to the DLL in `artifacts/native/x64`, staged by `NativeEngine.targets` into every output and the publish folder) names PuTTY's and our functions in a crash dump; code is the same as before. The flag reaches PuTTY's libraries only at a fresh configure (`CMAKE_C_FLAGS_INIT=/Z7` in `native/CMakeLists.txt`, which keeps the generator's `/DWIN32 /D_WINDOWS`): after changing it, delete `artifacts/native/x64/putty` (a from-scratch native build takes about 2 minutes).
- Why Ninja, measured for PuTTY's libraries from scratch: Ninja inside a VS developer environment configures in 25 s and builds in 51 s; the Visual Studio generator took 102 s and 107 s.
- Always build out-of-tree into `artifacts/` (git-ignored). Never build inside `external/putty`. A bash `cd` into it persists across tool calls in this environment, so use absolute paths.
- `plink` in `external/putty/CMakeLists.txt` is the template for which libraries an SSH client links. `guiterminal` bundles root `terminal/`, `ldisc.c`, `config.c`, `dialog.c` **plus** the Windows GUI files (`windows/dialog.c`, `controls.c`, ...), so link order matters if our engine defines its own `dlg_*` functions. The default engine links PuTTY's whole SSH client, backends, network code and portable terminal code (`terminal.c`, `bidi.c`, `lineedit.c`, `ldisc.c`, compiled directly), so `dotnet build` itself proves the front-end contract is met for all of that. The settings dialog's description (`config.c`, `dialog.c`) is compiled in too, with `native/engine/configbox.c` as its front end (the 30 `dlg_*` functions and `show_ca_config_box`), so the whole front-end contract of `docs/front-end-contract.md` is met at link time. The old `build\native.cmd x64 full` configuration, which was expected to fail and list what was missing, is gone.
- Shell traps in Git Bash: it rewrites MSVC-style `/flags` into paths (`dumpbin /nologo` fails), so `export MSYS_NO_PATHCONV=1`; and `cmd | tail` hides a failing exit code (a native build once reported exit 0 while failing), so use `set -o pipefail` and check `${PIPESTATUS[0]}`.

## Constraints that are not obvious

1. **PuTTY's CMake must be the top-level project.** It uses `${CMAKE_SOURCE_DIR}` about 96 times (including `charset/` and `cmake/gitcommit.cmake`). Never `add_subdirectory(external/putty)` from our own CMake; build it as a separate configure (for example via `ExternalProject`) and link its static libraries.
2. **No C++ file can include PuTTY headers.** `ssh.h` uses `new` as a vtable member name (lines 757, 834, 890, 1097). Code that talks to PuTTY (Seat, TermWin, LogPolicy, key translation) must be C. C++ (the Direct2D/DirectWrite renderer) sits behind a C interface.
3. **Keep `external/putty` pristine** so it can track upstream. Hooks the UI needs must live in our code or a fork branch. Example: the sketch's session inspector needs key-exchange, cipher and host-key fingerprint, and `putty.h` has no accessor for them.
4. **The core is single-threaded with global state** (timer queue, callback queue, PRNG, handle-wait list). `windows/handle-wait.c` asserts at most 64 waitable handles, and `cleanup_exit` terminates the process. Both matter once many sessions share one process.
5. **Never compile PuTTY code with `NDEBUG`** (`defs.h` errors out; assertions are part of its security model). `native/CMakeLists.txt` strips `/DNDEBUG` from the engine's flags. PuTTY's libraries are always built Release (`/MD`), so the engine always uses `/MD` too, even in its Debug configuration (mixing `/MD` and `/MDd` fails to link).
6. **The engine must define the functions PuTTY expects from a front end.** Linking `utils` alone needed only `modalfatalbox` and `cleanup_exit` (both in `native/engine/frontend.c`); the whole SSH client needed 14 more (printing, jump list, process-level), now defined in `frontend.c` or supplied by PuTTY's own stubs (`stubs/no-printing.c`, `windows/no-jump-list.c`), and the settings dialog still needs 31 (`docs/front-end-contract.md`). Do not link PuTTY's `guiterminal` library to make them go away: it bundles PuTTY's Win32 dialog code and silently hides what the engine must implement. Do not use `stubs/no-ca-config.c`: it is for programs without SSH code, and our engine links the real `ssh/ca-config.c`. The `Seat`, `TermWin` and `LogPolicy` obligations are runtime vtables the linker cannot check.
7. **PuTTY's assertions are live and mean it.** A crash like `Assertion failed ... tree234.c` kills the host process and is almost always misuse of a PuTTY API by our glue, not a PuTTY bug. Example seen: a timer scheduled with a `NULL` context (`schedule_timer(ms, fn, NULL)`) asserts in `run_timers`, because the context identifies the owner for `expire_timer_context`; timer contexts must be non-NULL. A second one: `conf_get_int(conf, CONF_tcp_keepalives)` asserts in `conf.c`, because that key is a boolean; the accessor must match the key's value type, so copy the call from `windows/window.c` or `windows/putty.c` instead of guessing (`conf_get_bool` here).

## NativeAOT + WinUI 3 on .NET 11 (verified on 11.0.100, first on rc.3, with Windows App SDK 2.6.5)

`PuTTY.App` is unpackaged (`WindowsPackageType=None`, self-contained Windows App SDK) and package-free by design; MSIX packaging is a separate step with `winapp package` (issue `putty-modern-apl`). The settings below live in `src/PuTTY.App/PuTTY.App.csproj` and each has a comment there; do not remove them without re-testing a NativeAOT publish **and** launching the result.

- **`UseOptimizedPublish=false`** (WindowsAppSDK [#6897](https://github.com/microsoft/WindowsAppSDK/issues/6897)): on the .NET 11 SDK, `PublishAot` turns on optimized publish, and XAML compilation then fails with `WMC1007`. This hits unpackaged apps too, not only single-project MSIX. The issue is fixed but unreleased. Re-tested on the 11.0.100 final SDK: removing the setting still fails (now as `MSB3030`, `PuTTY.App.pri` not found), so it stays.
- **`Microsoft.Windows.SDK.BuildTools.MSIX` pinned to 1.7.261102100** (WindowsAppSDK [#6394](https://github.com/microsoft/WindowsAppSDK/issues/6394), fixed from 1.7.260930100): Windows App SDK 2.6.5 pulls 1.7.251221100 transitively, so the pin relies on `CentralPackageTransitivePinningEnabled` in `Directory.Packages.props`. The publish output has no loose `.xbf` files (XAML is in `PuTTY.App.pri`) and the app starts fine.
- **`AllowUnsafeBlocks`** is required (CsWinRT error CsWinRT1030) because the docking library's types implement generic WinRT interfaces.
- **Under NativeAOT a WinUI class that managed code only ever receives from native code comes back as its nearest known base class** (cause of what used to be "the content of docked windows is silently dropped", Beads `putty-modern-sqm`, solved). The projection turns a native object into a managed one by its runtime class name; if the trimmer finds no use of that class, the lookup falls back to a base class, so `GetTemplateChild("PART_X") as ContentPresenter` is **null**, with no error. Measured in this app without any workaround: a `ContentPresenter` (from `XamlReader.Load`) came back as `FrameworkElement`, `Rectangle`, `Border` and `FontIcon` likewise, `Button` and `ToggleButton` and `ScrollViewer` as `ContentControl`/`ButtonBase`, `Canvas` as `Panel`, while `TextBlock`, `Grid` and `StackPanel` (constructed somewhere) were exact. `Digi21.WinUI.Docking` plugs its windows into a `ContentPresenter` it gets from its template, so the windows never appeared; its Close and pin buttons are `as Button` casts, so they did nothing. Constructing one instance of each such class in reachable code fixes it: `src/PuTTY.App/AotTypeAnchors.cs` (called from the `App` constructor) does that for the five classes the library casts to (`ContentPresenter`, `Rectangle`, `Border`, `Button`, `FontIcon`), and replaced the old `TrimmerRoots.xml` (a `DockSite` root), which fixed only `ContentPresenter` by accident: with it the Close button still did nothing. Verified on the 11.0.100 final SDK: no root plus the anchors gives 3 of 3 placeholders and a Close button that closes its window (invoked through UI Automation). **Whenever managed code casts a native object to a WinUI class it does not construct, add it to the anchors**, and check it by loading the class with `XamlReader.Load("<X xmlns='http://schemas.microsoft.com/winfx/2006/xaml/presentation'/>")` and looking at `GetType()`. The same applies to `FindName`, `VisualTreeHelper` and anything else that hands back an object created by native code. Not the cause, each tried: the library built from source against Windows App SDK 2.6.5 on net11, `IsAotCompatible`, wrapping every type in a trimmer root (`DockSite`, the containers, the whole assembly all "fixed" it only because they happen to keep some constructions alive).
- The write-up, including the original table of what was tried (which preserved types made the content appear), is in `docs/nativeaot.md` on the fork branch `nativeaot-readiness` ([drolevar/DockingPanels](https://github.com/drolevar/DockingPanels/tree/nativeaot-readiness)), together with a small library change (`AllowUnsafeBlocks`). The owner asked that any improvement to the library be done in that fork; nothing has been sent to the upstream repository, so ask before opening an issue or pull request there. A library-side fix (the same anchors inside `Digi21.WinUI.Docking`, so apps need nothing) is committed locally in the fork on branch `aot-template-part-types`, not pushed.
- **A C# subclass of a WinUI control must be `partial` for NativeAOT.** An unmarked one crashed the spike's AOT build at the first frame with `COMException 0x80040111 (ClassFactory cannot supply requested class)` naming `Windows.ApplicationModel.LimitedAccessFeatures`, which is misleading; the real signal was a **CsWinRT1028** warning ("isn't marked partial") that a filtered build log had hidden. Marking it `partial` fixes it (`spikes/keyboard-ime/SubclassProbe.cs`, `--probe-partial` / `--probe-plain`). **Read every CsWinRT warning in a NativeAOT publish**; do not grep the log for only `error|warning CS|IL`.
- WinUI template (`winapp new`) facts, if you scaffold another project: it targets net10 and is packaged by default, and it uses unpinned `Version="*"` references that must move into central package management.

## Planned architecture

```
external/putty/        submodule (pristine)                                   exists
native/                our C/C++ only: CMakeLists, CMakePresets, engine/      exists (C-ABI skeleton)
build/native.cmd       builds the native engine (CMake + Ninja, VS dev env)    exists
src/PuTTY.Native/      NoTargets project that runs build\native.cmd            exists
src/PuTTY.Interop/     LibraryImport declarations, AOT-compatible             exists
src/PuTTY.App/         WinUI 3 app, unpackaged, PublishAot, placeholder UI    exists
build/NativeEngine.targets  shared: build native first, stage the DLL          exists
tests/PuTTY.Interop.Tests/  MSTest, loads the real native engine               exists
spikes/keyboard-ime/   throwaway keyboard/IME experiment, not in PuTTY.slnx      exists
```

- **Layers:** PuTTY core (C) -> engine DLL (C glue plus C++ renderer, flat C ABI) -> `PuTTY.Interop` -> WinUI 3 app. Interop uses `LibraryImport`, `[assembly: DisableRuntimeMarshalling]`, blittable signatures and `[UnmanagedCallersOnly]` callbacks. Sessions are deliberately **not** `SafeHandle`s (see "Sessions" below). The engine starts as a DLL; static linking is a later option.
- **What gets replaced vs reused** (see the PuTTY map below): replace the `windows/` GUI group (`window.c`, `dialog.c`, `controls.c`, `config.c`, `putty.c`, `select-gui.c`, ...). Reuse the platform layer (`network.c`, `handle-io.c`, `storage.c`, `noise.c`, `serial.c`, `conpty.c`, `agent-client.c`, `sharing.c`, `gss.c`, `utils/`).
- **Threading (implemented in `native/engine/eventloop.c`):** the engine lives on the one thread that calls `pe_init`, which must run a Win32 message loop (the WinUI UI thread does; tests call `pe_pump`). A hidden message-only window receives `WM_NETEVENT` (forwarded to `winselgui_response`); `setup_gui_timing` supplies timers; `request_callback_notifications` posts a message that runs **one** deferred callback and re-posts while more are queued, like PuTTY's own loop, so window messages are not starved. Every other `pe_*` call from a different thread returns `PE_ERR_THREAD`. `pe_shutdown` closes sockets and drains messages before destroying the window (a stale entry in `select-gui.c`'s moribund-socket set would make a later socket that reuses a handle value ignore its events). Still to do: replace `handle-wait.c` with thread-pool waits.
- **Sessions (implemented in `native/engine/session.c`, managed side `src/PuTTY.Interop/PuttySession.cs`):** a `pe_session` owns a `Seat`, a `LogPolicy`, a `Conf` (from `load_open_settings(NULL, ...)` defaults for now), a `LogContext` and a `Backend`. Output, log lines, errors and close go to the host through the blittable `pe_session_events` table; the managed side turns them into `Output`/`Log`/`Error`/`Closed` events on the engine thread, and every `[UnmanagedCallersOnly]` callback catches all exceptions. Things that are easy to get wrong:
  - `PuttySession` is two-phase (construct, subscribe, then `Start()`) so the first lines of the event log are not lost: PuTTY logs "Connecting to ..." from inside `backend_init`.
  - `Closed` is raised **once**: PuTTY documents that `notify_remote_disconnect` may arrive more than once, even while `backend_connected()` is still true, so the glue ignores it until the backend says the connection is gone, and `connection_fatal` always closes; a flag makes whichever comes first the only notification.
  - A handler may dispose the session it is being called for. PuTTY is still on the stack inside the backend then, so `pe_session_close` from inside a callback marks the session `pending_close` (events are silenced at once) and queues the teardown with `queue_toplevel_callback`. A live-session list validates handles, so a stale `pe_session*` is rejected rather than dereferenced.
  - `PuttySession` is a plain `IDisposable`, not a `SafeHandle`: a `SafeHandle` is released on the finalizer thread, and the engine refuses calls from any thread but its own (`PE_ERR_THREAD`). A session that is never disposed is closed by `pe_shutdown` (`pe_sessions_close_all`), and disposing it afterwards is harmless.
  - Not done yet: `Seat` prompts (`get_userpass_input`), host-key and cipher confirmations (they fail safe through the `nullseat_*` defaults, slice 3), `Conf` is not yet configurable from the host. Warnings that belong to no session (`nonfatal()`, `old_keyfile_warning()`) are forwarded: `frontend.c` calls the handler set with `pe_set_warning_handler` (dropped by `pe_shutdown`, registered again by `PuttyEngine.Initialize`), which raises `PuttyEngine.Warning` on the engine thread; without a subscriber they only reach the debugger.
- **Renderer (`native/engine/render.cpp`, interface in `render.h`):** C++ (it cannot see PuTTY headers), Direct2D and DirectWrite, drawing a grid of cells one glyph per cell so fallback fonts cannot misalign it. Two targets with one drawing path: offscreen (a WIC bitmap, software, used by the tests: no window, no GPU) and a DXGI composition swap chain plugged into a XAML `SwapChainPanel` through `Microsoft.UI.Xaml.Media.DXInterop.ISwapChainPanelNative` (IID `63aad0b8-...`, not the UWP one). Panel drawing goes to a persistent canvas bitmap that is copied to the swap chain on each present, because a flip-model back buffer does not keep its contents and the emulator repaints only what changed. The panel path is not exercised until the terminal view exists (Beads `88o.5`). `pe_diag_render_text` / `PuttyEngine.Diagnostics.RenderText` draw text offscreen and report cell size and per-cell ink, which `RenderTests` use.

- **Folders and recents (`src/PuTTY.Sessions`, tests `tests/PuTTY.Sessions.Tests`, 16):** a plain NativeAOT-safe library (no WinUI, no native code) for what PuTTY's storage cannot hold, in a JSON file of its own, `%APPDATA%\PuTTY Modern\workspace.json` (never in the registry, never in a session's name, and not in `%APPDATA%\PuTTY`, which is PuTTY classic's). `SessionMetadata` holds folders (id, name, parent) and per-session entries keyed by the PuTTY name (folder, last opened, open count); `BuildTree(savedNames)` gives the panel's tree (folders first, by name, then sessions; a session in an unknown folder or one the file never heard of is at the top; sessions not in PuTTY's storage are not shown but **keep their entry**, `Prune` is the explicit way to forget); deleting a folder moves its contents up and loses nothing; sibling names are unique ignoring case; a folder cannot go into itself or its descendants, and a damaged file whose folders form a loop is shown with them at the top instead of hanging. `Recents` is derived from the last-opened times (no second list to drift). `MetadataStore` never throws for the file's state: missing is empty, **damaged is moved aside (`workspace.json.damaged-<time>`, kept) and loading gives empty**, **a file from a newer format version is shown but `Save` refuses**, unknown properties are ignored, and saving writes a temporary file next to it and moves it over (no half files). JSON uses the source generator (`MetadataJsonContext`). **Wired into the Sessions panel** (see there; `NoteOpened` records an opening, `Reload` reads the file again).
- **Settings window (`src/PuTTY.App/Settings/SettingsView.cs`, `SettingsWindow.cs`; New... and Edit... in the Sessions panel; check `tools/app-settings-smoke.ps1`):** PuTTY's own configuration box drawn from the engine's description, laid out as in the Figma sketch (frames `9:3` Session configuration and `9:4` Terminal preferences, which the owner redesigned with a **tree**, not a list, for the pages): a 256-px navigation pane (title "Settings", `AutoSuggestBox` "Find a setting", a "PAGES" caption, a `TreeView` of the page paths with the selected branch open, "About PuTTY" and Help), and on the right a `BreadcrumbBar`, the page title (last path element) and subtitle (PuTTY's own heading text), one **card** per group of controls (the theme's card fill and stroke, 4-px radius), and a bar with Restore defaults, Cancel, Save and **Open session** (the framework's `AccentButtonStyle`). It uses standard Fluent controls and theme brushes, which is what the sketch is drawn with. Presentation choices that differ from a literal rendering: **a check box is a `ToggleSwitch` with its label left and On/Off beside it**; a radio group whose buttons are Auto, Force on, Force off (PuTTY's three-way setting) is a **`SelectorBar`**, other radio groups stay `RadioButtons`; an edit box that does not take the full width is a label-left, box-right row; tab-separated list entries show as spaced columns; the Open button reads "Open session". Restore defaults is the Load of `Default Settings` (`SettingsDialog.LoadSavedSession`), and the footer Save is a second way to the Session page's own Save. "Find a setting" searches every control's label and goes to its page. The page cache, the `Quietly` flag that keeps PuTTY's own updates from echoing back as a user's edit, and the engine-side handlers are as described for the engine. Things learned: **`ListView.SelectedItems.Add` throws E_UNEXPECTED on a single-selection list that is not on screen**, set `SelectedIndex`; the tree and the pages are looked up by path, with a `Dictionary<TreeViewNode, string>` for the node that comes back from native code; winapp sees the tree as `TreeItem`s and a toggle by the name of its label. **The sketch's words (`Settings/Presentation.cs`, a table over the generic renderer):** PuTTY's group titles are whole sentences ("Specify the destination you want to connect to"), the sketch has short card titles with a line under them, so for the two pages it has frames for (Session 9:3, Terminal 9:4) a card is keyed by the page path and PuTTY's own group title and says "Connection", "Saved sessions", "Close window on exit", "Terminal emulation", "Line discipline", "Remote-controlled printing" and so on, with page subtitles; a group can become several cards (Answerback is a card of its own with its control on the right, `Card.Side`, `FromLabel` names where the next card starts; the untitled "Close window on exit:" group is keyed by the empty title); a label a card's title already says is hidden (`HiddenLabels`) but the control keeps PuTTY's label as its UI Automation name, which is what the smoke test finds it by. Any other page or group keeps PuTTY's own text (the rest of the 32 pages have no frame). Labels lose a trailing colon ("Connection type", "Other"), `Host Name (or IP address)` becomes "Host name (or IP address)". **The saved-sessions list shows each session's host and protocol on the right** (`PuttySessions.Describe`, re-read on each refresh, `Default Settings` has none). **The printer box shows "None (printing disabled)" when empty**: PuTTY's handler only does that for a NULL setting and the default is an empty string, so the unmodified core leaves it blank; selecting the matching list item is what makes an editable `ComboBox` show it (`Text` alone was not applied). **Windows fit the display** (`WindowSizing.Resize`: 1440x940 and 1120x860 are the sketch's, never more than the work area; the Sandbox screen is 1006x677). The smoke test scrolls the lower cards into view (`winapp ui scroll-into-view`) for a second picture of each page. Not done: pages the sketch has no frame for are generic.
- **Keyboard input (implemented in `native/engine/keys.c`; the design came from the spike, `docs/spike-keyboard-ime.md`):** keys come from the raw message stream, not from XAML events. A `WH_GETMESSAGE` hook on the engine thread, in C, hands key messages to `pe_translate_key` (PuTTY's `TranslateKey` with a short list of deliberate changes, written at the top of the file; keep it diffable against `windows/window.c`) and replaces them with `WM_NULL`, only while the app has called `pe_set_key_target` (`PuttySession.SetKeyboardTarget`, from the terminal view's focus events) for a session that has a terminal; `VK_PROCESSKEY` and `VK_PACKET` key-downs pass through and `WM_CHAR` is taken as text. The tests (`KeyboardTests.cs`) inject nothing into the desktop: they post the messages Windows would to the engine thread, describe held modifiers with `SetKeyboardState`, activate a layout on that thread, and read the bytes that reach a loopback server. Two things that cost time: a Raw session edits the line locally by default (the line discipline holds typing until Enter), so tests call `SetLocalEchoAndEditing(Off, Off)`; and the engine sends UTF-8 (`CONF_line_codepage` is set when the terminal is enabled). On four layouts (en-US, nb-NO with dead keys and AltGr, ru-RU, uk-UA) this matched Windows' own translation for text, dead keys, AltGr, Unicode and CapsLock, and XAML cannot match it elsewhere: a handled `KeyDown` suppresses `CharacterReceived`, `Alt+Space` still opens the system menu, Alt+key characters are not delivered, Tab arrives with scan code 0 and `VK_PACKET` as 0xFF. `CoreTextEditContext` is not usable in WinUI 3 desktop (no HWND interop). **IME: the route is the proxy `TextBox`, implemented; composition itself is still unverified.** Measured with a real text service (Rime Weasel, installed in the Sandbox with `winget install Rime.Weasel`, which needs no language pack): pinyin typed into the custom terminal arrived as plain Latin letters (`nihao`), so a control with no text store gets no IME at all, and the IMM32-handlers route cannot work. `TerminalViewController` therefore keeps a real `TextBox` (AutomationId `TerminalInput`) that **holds the keyboard focus** and sits at the terminal's cursor (`pe_terminal_events.cursor` / `PuttySession.CursorMoved`, reported when the cursor changes cell, so the IME's candidate window opens there); the engine's message hook still takes every plain key first and leaves `VK_PROCESSKEY` to TSF; what the box gets, committed composition, emoji panel, voice typing, goes to `PuttySession.TypeText` (`pe_session_type_text`: `term_keyinputw`, the path `window.c` gives WM_CHAR text) and the box is emptied. **Two traps found: a `TextBox` at opacity 0 never raises `TextChanged` (WinUI raises it in a render pass), so the resting opacity is 0.01; and `TextChanged` did not fire at all for text set through UI Automation, `TextChanging` (scheduled on the dispatcher, because `Text` is not updated yet when it fires) does, so the box listens to both.** Checked: engine tests for `TypeText` (UTF-8, an emoji as a surrogate pair) and the cursor reports, and the terminal smoke test puts "é你😀" into `TerminalInput` through UI Automation and sees its UTF-8 on the server. **Not checked: an IME composing into the box.** In this guest Weasel does not compose at all, not even in a plain WinForms edit box (control experiment: `nihao ` came out raw after the profile was activated, a Shift tap changed nothing), so `tools/app-ime-smoke.ps1 -Smoke ime` stops at its last check there; it is kept for a machine where an IME works (and it shows the way: `ITfInputProcessorProfileMgr::ActivateProfile` with `TF_IPPMF_FORSESSION` switches the session's input method, `SendInput` types, a whole-screen `CopyFromScreen` shows the IME's own candidate window). Beads `88o.7`.
- **Settings dialog, engine side (`native/engine/configbox.c`; managed `SettingsDialog` in `PuTTY.Interop`; tests `SettingsDialogTests`, 16):** PuTTY's own configuration box, `config.c`'s tree of about 200 controls on 32 pages with its own handlers, runs headless in the engine and the host draws it. `pe_config_open` builds the control tree (`setup_config_box`) on a fresh `Conf`; `pe_config_describe` emits every group and control as flat records (`SettingsGroup`, `SettingsControl`: type, flags, column start and span, percent width, list height, radio labels and shortcuts, file filter, `AlignNextTo`); `pe_config_refresh` has PuTTY fill all controls from the `Conf`. **The engine keeps the state of every control** (text, check, radio, list entries with ids and selection, file, font, colour) because handlers read it straight back (the session list) and the host may not have drawn the page; it tells the host `ControlChanged(id)` and the host reads with `GetText/GetChecked/GetRadio/GetList/GetFile/GetFont`. The host reports what the user does (`SetText`, `SetChecked`, `SetRadio`, `Select`, `Act`, `SetFile`, `SetFont`, `ColourChosen`, `Focused`, `SetPage`) and PuTTY's handlers answer with more changes. `Ended(true)` is Open (the settings name a host, else PuTTY beeps), `CreateSession()` then opens a session from the edited `Conf`; the Session page's Save, Load and Delete are PuTTY's own handlers writing PuTTY's own storage. Things that cost a round or are easy to get wrong: **`struct dlgparam` is already defined by `windows/controls.h`**, so the dialog object itself is passed as the `dlgparam *` by a cast; **a handler may call `dlg_end` and the host may dispose the dialog inside that very callback**, so teardown is deferred while anything runs (`busy`, a queued top-level callback); **a new `Conf` has port 0 unless `settings_set_default_protocol` and `settings_set_default_port` were called** (window.c does it at start-up, `pe_init` now does); **SSH and Serial are the only protocol radio buttons**: Telnet, Rlogin, Raw and SUPDUP are in the drop-down list that goes with "Other:" (the tests' `ChooseProtocol` does both); the dialog **always lists `Default Settings` first** in the saved-sessions list; the Open and Cancel buttons are in a group on no page (empty path); the first values are in place when `SettingsDialog.Open` returns, so a host cannot subscribe to them. **Change Settings on a running session** (`pe_config_open_for_session`, `pe_config_apply`, managed `SettingsDialog.OpenForSession(session)` / `IsMidSession` / `Apply()`; tests `ReconfigureTests`, 4): `setup_config_box(box, midsession=true, protocol, backend_cfg_info(backend))` on a copy of the session's Conf (`term_pre_reconfig` first, so that leaving the title box alone keeps the title), with no host name and a default button that says Apply; the host calls `Apply()` when `Ended(true)` arrives, which copies the edits INTO `s->conf` (**the line discipline, key translation and the emulator's helpers hold pointers to that Conf, so never replace it**) and runs `windows/window.c`'s IDM_RECONF sequence: `log_reconfig`, `ldisc_configure` + `ldisc_echoedit_update`, `term_reconfig` (colours, wrap, title and the rest are PuTTY's own), our `pe_termwin_use_settings`, `term_size` if the scrollback length changed, `term_invalidate`, `backend_reconfig`. A session is named by pointer **and a serial number that is never reused** (`pe_session.serial`), because a dialog may outlive its session and a new one can get the same address: Apply on a gone session is `PE_ERR_STATE`; `pe_config_start_session` refuses such a dialog (the refusal shows at `Start()`, `CreateSession` is two-phase). In the app: the **Session details** panel (`SessionDetailsController`: name, where it connects, Connected or not, and the Session settings button `ChangeSettingsButton`, enabled while connected) opens the settings window in this mode (title "Session settings - name", Apply instead of Open session, no Restore defaults); the smoke test changes the window title on the Behaviour page and watches the app's window title follow. Not done: the font and window-size settings of a running session (our renderer takes its font from the host, `pe_session_set_font`, not from CONF_font), host-CA editing (`show_ca_config_box` tells the user it is unavailable), and the details panel's key exchange, cipher and host-key rows (the engine has no accessors). The UI plan: a generic renderer over this description plus a presentation overlay; the sketch covers only 17 of the 32 pages (no Telnet, Rlogin, SUPDUP, Selection/Copy or the 11 SSH sub-pages).

## Beads Issue Tracker

This project uses **bd (beads)** for issue tracking. Run `bd prime` to see full workflow context and commands.

### Quick Reference

```bash
bd ready              # Find available work
bd show <id>          # View issue details
bd update <id> --claim  # Claim work
bd close <id>         # Complete work
```

### Rules

- Use `bd` for ALL task tracking — do NOT use TodoWrite, TaskCreate, or markdown TODO lists
- Run `bd prime` for detailed command reference and session close protocol
- Use `bd remember` for persistent knowledge — do NOT use MEMORY.md files

**Architecture in one line:** issues live in a local Dolt DB; sync uses `refs/dolt/data` on your git remote; `.beads/issues.jsonl` is a passive export. See https://github.com/gastownhall/beads/blob/main/docs/core-concepts/sync-concepts.md for details and anti-patterns.

## Agent Context Profiles

The managed Beads block is task-tracking guidance, not permission to override repository, user, or orchestrator instructions.

- **Conservative (default)**: Use `bd` for task tracking. Do not run git commits, git pushes, or Dolt remote sync unless explicitly asked. At handoff, report changed files, validation, and suggested next commands.
- **Minimal**: Keep tool instruction files as pointers to `bd prime`; use the same conservative git policy unless active instructions say otherwise.
- **Team-maintainer**: Only when the repository explicitly opts in, agents may close beads, run quality gates, commit, and push as part of session close. A current "do not commit" or "do not push" instruction still wins.

## Session Completion

This protocol applies when ending a Beads implementation workflow. It is subordinate to explicit user, repository, and orchestrator instructions.

1. **File issues for remaining work** - Create beads for anything that needs follow-up
2. **Run quality gates** (if code changed) - Tests, linters, builds
3. **Update issue status** - Close finished work, update in-progress items
4. **Handle git/sync by active profile**:
   ```bash
   # Conservative/minimal/default: report status and proposed commands; wait for approval.
   git status

   # Team-maintainer opt-in only, unless current instructions forbid it:
   git pull --rebase
   git push
   git status
   ```
5. **Hand off** - Summarize changes, validation, issue status, and any blocked sync/commit/push step

**Critical rules:**
- Explicit user or orchestrator instructions override this Beads block.
- Do not commit or push without clear authority from the active profile or the current user request.
- If a required sync or push is blocked, stop and report the exact command and error.
